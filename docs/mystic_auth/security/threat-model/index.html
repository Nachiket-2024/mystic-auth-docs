Threat Model

New to a term here? See the Authentication Glossary or Infrastructure Glossary.

A short threat model for MysticAuth: what it protects, who might attack it, where the trust boundaries are, and which control answers each threat. It uses the STRIDE categories (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). Review it whenever a new sign-in method, a new data store, or a new public route is added.

This is a design-level document written from the code and docs. It is not a penetration test result. Controls named here link to the page that explains them.

What we protect​

AssetWhy it matters
Password hashes (Argon2id)Offline cracking if the database leaks
Sessions and tokens (access, refresh)Taking one is taking the account
Passkey public keys and credential idsLow value alone, but they decide who can sign in
Policies and permission grantsChanging them changes who can do what
The security audit logThe evidence trail after an incident
Email, name and profile dataPersonal data, plus the verification and reset channel
Secrets (SECRET_KEY, database passwords, backup key, OAuth client secret)Forging tokens, reading or restoring data
BackupsA full copy of everything above

Who we defend against​

ActorCan doCannot do
Anonymous internet userHit public routes, guess passwords, try signup and reset flows, send crafted inputReach Postgres or Valkey directly
Authenticated ordinary userUse their own account, try to reach other accounts or higher permissionsGrant themselves permissions they do not hold
Holder of a narrow permission (for example policies:create)Use that permissionMint or assign anything they do not already hold
Attacker with a stolen session or refresh tokenAct as the user until it is revokedRe-use a rotated refresh token without it being detected
PhisherTrick a user into typing a passwordUse a passkey on a fake site
Compromised dependencyRun code inside the backend or frontendBe assumed away: this is why CI scans dependencies
Operator mistakeMisconfigure CORS, proxies, secretsBe fully prevented; checks exist but a human still deploys

Out of scope: an attacker with root on the host, a compromised database superuser, and a compromised identity provider (Google).

Trust boundaries​

Everything from the browser is untrusted, including cookies, headers, the Origin, and any client-side check. The frontend only hides what the user may not do. The backend decides.

Threats and controls​

Spoofing (pretending to be someone)​

ThreatControl
Password guessing and credential stuffingPer-IP and per-account rate limits, source-scoped lockout, Argon2id, see Abuse prevention
Learning which emails are registeredGeneric responses, signup always returns the same body, dummy-hash timing, see Timing-attack resistance
Stolen session cookieHttpOnly, Secure, SameSite=Strict, short access token, rotating single-use refresh token with reuse detection, per-session revoke and sign out everywhere
PhishingOptional passkeys are bound to the site, so a fake site cannot use them
Forged tokensSigned JWTs with pinned algorithm, issuer and audience, SECRET_KEY strength enforced at start-up
Fake OAuth callbackoauth_state cookie and PKCE, see OAuth2 PKCE
Spoofed client IPX-Forwarded-For trusted only from TRUSTED_PROXY_IPS, see Reverse-proxy IP trust

Tampering (changing data)​

ThreatControl
SQL injectionSQLAlchemy parameterised queries, Pydantic schemas on every route
Cross-site request forgerySameSite=Strict cookies, restricted CORS to the configured origins, JSON-only bodies
Editing the audit trailThe application database role has UPDATE and DELETE on the audit log revoked
Tampering with a backupDetached HMAC-SHA256 tag checked before restore, see Database backup
A caller widening their own permissionsassert_authorized_to_grant blocks granting anything the caller does not hold, with mutation-checked tests
Replaying a one-time linkVerification, reset and deletion tokens are single use and expire

Repudiation (denying an action)​

ThreatControl
"I never did that"Security audit log for sign-in, logout, passkey, role, policy and lifecycle events, with IP, user agent and request id
Operator actions on another accountAudited with the acting user, for example removed_by on operator passkey removal
Silent credential changesThe account holder is emailed when a passkey is added or removed

Information disclosure (leaking data)​

ThreatControl
Stack traces or internals in errorsGlobal handler returns a generic 500, debug is never enabled
Secrets in logs or URLsNo secrets in the audit log, email links carry tokens in the URL fragment, Referrer-Policy: no-referrer
Cached sensitive responsesCache-Control: no-store on every API response
Leaked database dumpPasswords are hashed; backups are encrypted
Cross-origin readsCORP, COOP, COEP and strict CSP, see HTTP layer
Cross-site scriptingReact escaping, html.escape in emails, CSP without inline script or style allowances
Leaked repository secretsgitleaks over full history in CI

Denial of service (making it unavailable)​

ThreatControl
Request floods against auth routesLayered rate limits and lockout
One attacker locking out a victimLockout is scoped to the account and source IP pair, not account-wide
Expensive hashing used as a weaponRate limits sit in front of Argon2; passwords are capped at 128 characters
Valkey outageRate limiting fails closed by design; this trades availability for safety, an accepted decision
Oversized or malformed requestsPydantic length caps, nginx header and URI limits

Elevation of privilege (gaining more access)​

ThreatControl
Missing authorization on a routeDeny by default, require_authorization on each route
Acting on a more privileged accountusers:manage_privileged required when the target holds the admin role; the system account is untouchable through generic routes
Using a narrow permission to reach a broad oneGrant guard, policy history rollback checks, resource-type repointing checks
Over-privileged database accessApplication connects with a least-privilege role, tested in test_least_privilege_db_role.py
Compromised dependencypip-audit, npm audit, trivy, SBOM, manual batched upgrades

Residual risks we accept​

These are decisions, not oversights. Open ones are tracked on the Concerns page.

  • No multi-factor authentication, by choice. Password or Google sign-in is the main path, and optional passkeys are offered instead of a forced second factor.
  • Password rules are 8 characters with upper, lower and digit, and no breach check.
  • Authorization decisions can be up to 60 seconds stale after an out-of-band permission write.
  • A thief replaying a refresh token from the same IP and user agent inside the 10-second grace window looks like the real device.
  • A Valkey outage stops authentication (fail closed).
  • Plus-addressed and Unicode look-alike emails can create separate accounts. Email verification still requires a working mailbox, and a look-alike cannot receive the real person's mail, so this gives no account access. A product that limits things per person (free trials, credits) should add its own control, such as phone or card checks, or a normalised-email duplicate flag.
  • No point-in-time database recovery; backups are periodic dumps.
  • No TLS between containers on the same host's private network.

When to update this page​

  • A new sign-in method, token type, or public route.
  • A new place that stores personal data or secrets.
  • A change to which proxy or tunnel sits in front of the API.
  • After any security incident.
