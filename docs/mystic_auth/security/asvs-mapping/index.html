ASVS Level 3 Mapping

New to a term here? See the Authentication Glossary or Infrastructure Glossary.

A self-assessment of this template against the OWASP Application Security Verification Standard (ASVS) version 4.0.3, Level 3. Level 3 includes every Level 1 and Level 2 requirement, so this page covers all three.

How to read it. This is a desk review of the code, tests, CI and docs on 2026-11-03. It is not a penetration test and not an audit by an outside party. A status is only "Met" when the evidence column points at something that was read in this pass. Anything not read is "Not verified", never "Met".

StatusMeaning
MetImplemented and evidenced in code, config, tests or CI
PartialImplemented in part, or only for some paths
GapNot implemented, or implemented below the ASVS bar
DeploymentDepends on the operator's host, bucket, DNS or TLS, so the template alone cannot satisfy it
N/AThe feature does not exist in this template (for example file upload)
Not verifiedNot examined in this pass

Requirement numbers are ASVS 4.0.3 numbers. Only requirements this pass could tie to evidence are cited by number; the rest of each chapter is described by theme.

Summary of gaps​

These are the findings that matter most for a Level 3 claim. None is a new vulnerability; most are documented scope decisions.

#ASVSGapWhere it is recorded
1V2.1.1, V2.1.7, V2.1.9Password policy is 8 characters minimum with upper, lower and digit rules. ASVS wants at least 12 characters, a check against breached passwords, and no composition rules. I accepted this as a product decision.password_service.py::validate_password_strength, mirrored in passwordRules.ts
2V2.8, V2.9, V4.3.1No multi-factor authentication. Passkeys are an optional single-step sign-in, not a second factor. L3 expects MFA for privileged management interfaces. I accepted this: password or Google sign-in is the main path, and I offer optional passkeys instead of a forced second factor, which would add daily friction.Why MFA is not enabled
3V6.2, V6.4Rotation of passwords held by a running service (database, Bugsink, Valkey) is manual.Rotating secrets
4V9.1Plain connections between backend, Postgres and Valkey inside the single-host compose network, which is isolated with internal: true networks. Multi-host deployments must add TLS (documented, untested here). Transport protection to the browser is handled by the reverse proxy or tunnel.Deployment
5V8.3No point-in-time recovery, so up to one backup interval (hourly in the production example) of data can be lost.Database backups
6V14.2No automated dependency-update bot (deliberate, CVEs are still scanned by pip-audit, npm audit and trivy).Dependency updates

Items marked Deployment cannot be closed by the template. They need a real host and are listed in the Concerns page and the Downstream Project Launch Checklist.

Level 3 specific notes​

Level 3 adds depth rather than new chapters. For this template the L3-only items are:

  • Architecture review and threat modelling (V1): a design-level threat model exists; an independent architecture review has not been done.
  • Multi-factor authentication for privileged management access (V2.8, V4.3.1): not implemented, by my choice; I offer optional passkeys instead (see Why MFA is not enabled).
  • Cryptographic key management with a vault or HSM (V6.4): not in scope for a template; keys live in env files.
  • Separation of duties and tamper-evident audit logs (V7, V4): the application role cannot edit or delete audit rows, but a database superuser still can. Shipping logs to an external append-only store is a deployment choice.
  • Verified build provenance (V10, V14): an SBOM is produced, but images are not signed or attested. Not applicable while images are built on the host that runs them, because there is no registry hop to protect. Revisit signing (for example cosign) together with a registry push if images are ever pulled onto other hosts.

Suggested order to close gaps​

  1. If images start being pushed to a registry and pulled onto servers, sign them and publish provenance in CI (V10, V14).

Out of scope: export-control classification​

Whether the cryptography in this template needs an export classification (for example under US EAR) is a legal question for whoever distributes the product. This page does not make that determination. My decision (2026-11-03): I plan to run this as a hosted service from Sydney or Mumbai, so I distribute no software to customers. I will revisit this and get advice if I ever ship the software (downloadable, on-premise or published) or sell to government or defence buyers.
